1. 為什麼需要這一步

Jetson 接著攝影機，放在現場（家裡、工地、無人機地面站）。想看畫面的人不在現場，他們用手機或電腦的瀏覽器，從網路上的某個網址看。 所以中間需要一台大家都連得到的雲端伺服器：Jetson 把畫面「推」上去，瀏覽器再從伺服器「拉」下來。 兩個專案用的都是 https://skai-cam.duckdns.org/sfu/cam1/whip 這台伺服器上跑的 minisfu （由另一個 repo skai-edge-streaming-infra 維護）。

聽起來只是「把資料傳上去」，為什麼不直接用 HTTP 上傳檔案？因為有三個要求同時存在：

  • 要即時：延遲要在一秒以內。HTTP 上傳檔案要等一段影片存好才送，延遲是好幾秒起跳。
  • 要能穿過路由器：Jetson 的 IP 是 172.16.1.50 這種區網位址，外面的人看不到它。資料要能從「路由器後面」送出去，而且伺服器回傳的封包要能找回來。
  • 要加密：影像會經過公開網路。

WebRTC 是瀏覽器內建的一整套即時影音傳輸技術，剛好把這三件事都包了。 但 WebRTC 本身沒有規定「雙方一開始怎麼接上頭」， WHIP（WebRTC-HTTP Ingestion Protocol）就是補這個洞的標準：用一次 HTTP POST 完成接頭。 Step 27 要做的，就是在本 repo 裡實作一個 WHIP 推流端。skai-edge-cpp 早就有一個，所以這一章拿它當對照組。

3. 一次推流的完整旅程

不管是哪個專案，一次推流都會經過下面這九步。兩個專案的差別只在於每一步由誰負責。 圖上每一個步驟都可以點，會跳到對應的小節；第 5–11 節標題後面的「（步驟 ①）」這類標記，用的就是這張圖的編號。

先記住一件事：HTTP 只用來「約好怎麼連」（④⑤）和「說再見」（⑨）。約好之後，影像是用另一條 UDP 連線直接送到伺服器，跟 HTTP 無關。 所以 token 只出現在 HTTP 請求裡；本 repo 的 README 也寫明「RTP media does not use it」。

4. 誰負責哪一層

把圖 27.2 的工作拆成六層，再看兩個專案各自怎麼分配。顏色是重點：黃框是自己寫的，藍框是交給函式庫的。

為什麼本 repo 的 ICE 是自己寫的？skai-ice 原本是從 skai-edge-cpp 的區網 WebRTC 功能（webrtc_native_node）抽出來的學習專案。 它刻意做成跟 libjuice（libdatachannel 預設的 ICE 函式庫）一樣的介面，所以 libdatachannel 可以直接拿它當替身。 本 repo 的 CMakeLists.txt 就是這樣接的：

CMakeLists.txt（節錄）
set(USE_SYSTEM_JUICE ON CACHE BOOL "" FORCE)
…
add_subdirectory(third_party/skai-ice EXCLUDE_FROM_ALL)
…
add_subdirectory(third_party/libdatachannel EXCLUDE_FROM_ALL)

USE_SYSTEM_JUICE=ON 的意思是：libdatachannel 不要自己建 libjuice，改去連一個叫 LibJuice::LibJuice 的現成 target（CMake 裡「一個可以被連結的函式庫」的名字）。skai-ice 的 CMakeLists 剛好替自己取了這個別名：

third_party/skai-ice/CMakeLists.txt
add_library(LibJuice::LibJuice ALIAS skai_ice)

所以 skai-ice 一定要比 libdatachannel 先 add_subdirectory：libdatachannel 找這個名字時，找到的就是 skai-ice。 本 repo 在 Step 23–26 為了區網瀏覽器觀看（WHEP）接上這套 ICE；Step 27 的 WHIP 推流沿用同一套。 這個選擇帶來的後果，第 7 節會詳細講。

為什麼不直接用 webrtcbin？

webrtcbin 做得到，cpp 就是證明。本 repo 不用它，是因為 ROADMAP.md 明文規定。§4.7「One WebRTC/ICE stack」的規則：

ROADMAP.md（§4.7，節錄）
### 4.7 One WebRTC/ICE stack
…
- `skai-ice` remains an independent repository and is consumed as a pinned dependency.
…
- do not use GStreamer `webrtcbin`
- do not link libdatachannel's normal libjuice backend by mistake

ROADMAP 最後的架構原則清單又寫了一次，而且講的是「整個應用程式」，不只瀏覽器觀看：

ROADMAP.md（架構原則清單，節錄）
14. libdatachannel owns PeerConnection, DTLS, SRTP, and RTP.
15. `skai-ice` is the only ICE implementation used by this application.
…
17. Do not use `cpp-httplib`, MediaMTX, or `webrtcbin` as a hidden second WebRTC path.
18. First WebRTC release is LAN/host-candidate only.
19. NAT traversal improvements belong in `skai-ice`.

§4.7 那兩條的意思：skai-ice 是另一個獨立的 repo，本 repo 用 git submodule 把它固定在某一個 commit（這就是 pinned dependency，third_party/skai-ice 就是那個 submodule）； 另外要小心別讓 libdatachannel 連到它自己附的那份 libjuice。清單那幾條翻成白話：

  • 第 14 條：PeerConnection、DTLS、SRTP、RTP 都歸 libdatachannel。
  • 第 15 條：整個程式只能有一套 ICE，就是 skai-ice。
  • 第 17 條：不准另外塞一條 WebRTC 路。點名的三個，webrtcbin 會帶進自己的 ICE 與加密；MediaMTX（第 8 節會提到的現成串流伺服器）可以代做 WebRTC；cpp-httplib 是一套 HTTP 函式庫，skai-ice 附的獨立 WHEP 服務用它處理信令。三者都會繞過上面那條唯一的路。
  • 第 18 條：第一版本來就只做區網、只有 host 候選。
  • 第 19 條：要穿越 NAT，就去改 skai-ice。

webrtcbin 內建的 ICE 是 libnice，用了它，程式裡就會有兩套 ICE，直接違反第 15、17 條。 Step 27 的 WHIP 推流雖然是雲端用途，但它跟區網觀看在同一個執行檔裡，同樣受這幾條約束。 所以本 repo 用 skai-ice 是 ROADMAP 定下的架構規則，不是寫 Step 27 的人的個人偏好。 至於為什麼要訂「只能一套 ICE」，ROADMAP 沒有寫理由，只在「不做的事」清單裡列了 a second ICE implementation inside this repository。 本章不替它補理由；要重新評估這條規則，得先找當初訂規則的人問清楚。

另一個常被問到的問題：那可以只讓 WHIP 這一路改用 libdatachannel 原本的 libjuice（它支援 STUN 與 TURN）嗎？ 在同一個執行檔裡不行。USE_SYSTEM_JUICE 是整個 libdatachannel 的建置開關，不是每條連線各自選的。 而且 skai-ice 自己就實作了 libjuice 那一整組 juice_* 函式（juice_create、juice_gather_candidates、juice_send……，在 third_party/skai-ice/src/juice_shim.cpp）。 一個程式裡同名的函式只能有一份，兩者都連進來，不是連結失敗，就是不聲不響地只用到其中一份。 後者更糟：用到哪一份取決於連結順序，可能區網觀看或 WHIP 其中一邊悄悄跑了你以為沒用的那套 ICE，而且沒有任何錯誤訊息。 CMakeLists.txt 有一道檢查專門擋這種情況。juice、juice-static 是 libjuice 自己的 CMake 會建出的 target 名稱， 只要出現就代表多了一份 libjuice；FATAL_ERROR 會讓 cmake -S . -B build 那一步直接失敗，連編譯都不會開始：

CMakeLists.txt
if(TARGET juice OR TARGET juice-static)
    message(FATAL_ERROR "libdatachannel built a duplicate libjuice; USE_SYSTEM_JUICE must remain ON")
endif()

所以改用原版 libjuice，不能只換 WHIP 這一路。想讓 WHIP 有 STUN/TURN，剩下兩條路：補強 skai-ice（全程式一起受益）， 或只讓 WHIP 改用 webrtcbin（技術上做得到，但要推翻上面的第 15、17 條）。兩條路的代價，以及為什麼建議先實測，見本章末的目前限制。

skai-edge-native 是單一執行檔。RTSP 模組每收到一張攝影機送來的畫面，就直接呼叫一個 callback，同時交給區網 WebRTC 與 WHIP 推流：

            webrtc_manager->publish_access_unit(unit);
            whip_sink->publish_access_unit(unit);

這裡沒有重新編碼：送上雲端的就是攝影機原本的 H.264（前一個 PR #31「Pass source H.264 through」做的事）。 好處是省下 Jetson 的編碼運算、延遲更低；代價是碼率與解析度由攝影機決定，通常比 480p 大很多，上行頻寬要夠。 publish_access_unit 只是把畫面放進一個最多裝 8 張的佇列（BoundedQueue<EncodedAccessUnit> media_queue_{8}）， 真正的發送在另一條 worker thread 上做，所以 RTSP 那邊不會被網路卡住。

6. 建立 offer：告訴對方「我要送什麼」（步驟 ②）

skai-edge-cpp：寫一條 GStreamer pipeline

GStreamer 的程式是用「元件串成管線」的方式組起來的。skai-edge-cpp 的整個 WebRTC 推流端就是一行字串：

skai-edge-cpp：src/skai_edge_perception/src/nodes/selfhost_publisher_node.cpp
    const char* desc =
        "appsrc name=whip_src is-live=true do-timestamp=true format=time "
        "  caps=video/x-h264,stream-format=byte-stream,alignment=au "
        "! h264parse config-interval=-1 "
        "! rtph264pay pt=96 config-interval=-1 aggregate-mode=zero-latency "
        "! application/x-rtp,media=video,encoding-name=H264,payload=96,clock-rate=90000 "
        "! webrtcbin name=sendrecv bundle-policy=max-bundle latency=0";

讀法是由左到右，! 是「接到下一個元件」：appsrc（程式把畫面塞進來的入口）→ h264parse（整理 H.264）→ rtph264pay（切成 RTP 封包）→ webrtcbin。 webrtcbin 是一整包 WebRTC：建 offer、ICE、DTLS、SRTP 全在裡面。 程式只要在它發出 on-negotiation-needed 訊號（「我準備好了，可以建 offer 了」的事件通知）時呼叫 create-offer，拿到 offer 後再呼叫 set-local-description。

字串裡還有兩種東西不是元件。像 application/x-rtp,… 這種沒有元件名、只有一串格式描述的段落叫 caps（capabilities）：它不做任何處理，只規定「流過這裡的資料必須是這個格式」；appsrc 後面的 caps=video/x-h264,… 是同一種東西，告訴 GStreamer 塞進來的是哪種 H.264。其餘 config-interval=-1 這類是各元件的參數，本章不需要懂。

「local description」是自己這端的 SDP，「remote description」是對方的。建出 offer 只是產生一份文字；要 set-local-description 之後，函式庫才會照這份內容真的開始準備（例如開始 ICE gathering）。拿到伺服器的 answer 時，則要 set-remote-description。libdatachannel 的 setLocalDescription / setRemoteDescription 是同一件事。

逐行講：

  • addH264Codec(96)：宣告「我送 H.264，封包上標編號 96」。96 只是雙方約定的代號，在 SDP 裡會寫成 a=rtpmap:96 H264/90000。
  • addSSRC：SSRC 是這一路影像的身分證號碼，每個 RTP 封包都會帶著。
  • SendOnly：明講「我只送不收」。
  • H264RtpPacketizer：把一張畫面切成 RTP 封包。StartSequence 表示輸入是 Annex-B 格式（用 00 00 00 01 分隔每一段），也就是攝影機送出來的格式。
  • RtcpSrReporter：定期告訴對方「我這邊的 RTP 時間對應真實時間幾點」，接收端靠它同步。
  • RtcpNackResponder：對方回報「第 N 號封包沒收到」（NACK）時，重送那個封包。webrtcbin 這些是內建的，這裡要自己掛上去。

那本 repo 怎麼連到雲端？

以下是推論。本章作者沒有實測本 repo 對雲端的端到端推流；Step 27 修正時另有一次在這台 Jetson 的網路上成功的回報（見目前限制），但沒有記錄當時的 NAT 情況，所以下面的條件仍然是推論。

Jetson 的 offer 裡只有 172.16.1.50，雲端伺服器從網路上連不到這個位址。 但伺服器的 answer 裡會有它自己的公開位址。Jetson 照著 answer 去打那個位址時，封包經過 NAT 出去， NAT 會記住「這個埠的回應要轉給 172.16.1.50」。伺服器收到之後，把來源位址當成一個新的候選（ICE 稱為 peer-reflexive），往回送的封包就能沿著這個洞回來。

這條路要成立，得同時滿足：Jetson 的網路允許 UDP 往外送、NAT 不是最嚴格的那種、伺服器端的 ICE 會接受 peer-reflexive 候選。 任何一個不成立就連不上，而本 repo 沒有 TURN 可以退。cpp 在同樣情況下還有 TURN 可以用。

8. WHIP：用 HTTP 交換 offer 與 answer（步驟 ④⑤⑥）

    const auto origin = endpoint.substr(0, authority_end);
    if (location.empty()) {

RTP 時間戳

每個 RTP 封包都要蓋時間戳，單位是 1/90000 秒（SDP 裡的 H264/90000）。接收端靠它決定每張畫面什麼時候播。

  • cpp：把 PTS 設成「不知道」（GST_BUFFER_PTS(buf) = GST_CLOCK_TIME_NONE），讓 appsrc do-timestamp=true 用「畫面抵達的時間」自動蓋。簡單，但網路或 ROS 傳遞的抖動會直接變成播放的抖動。
  • 本 repo：用攝影機給的 PTS（呈現時間，奈秒）換算：h264_rtp_timestamp 就是「秒 × 90000 ＋ 餘數換算」。攝影機沒給 PTS 時，退回每張 +3000（等於假設 30 fps）。
include/skai/video/encoded_access_unit.hpp
inline std::uint32_t h264_rtp_timestamp(std::uint64_t pts_ns) noexcept {
    const std::uint64_t seconds = pts_ns / 1'000'000'000ULL;
    const std::uint64_t remainder = pts_ns % 1'000'000'000ULL;
    return static_cast<std::uint32_t>(seconds * 90'000ULL +
                                     remainder * 90'000ULL / 1'000'000'000ULL);
}

            if (!stopping_) logger_.log(LogLevel::Error, "whip", error.what());
            return;
        } catch (const std::exception& error) {
            if (!stopping_) logger_.log(LogLevel::Error, "whip", error.what());
        } catch (...) {
            if (!stopping_) logger_.log(LogLevel::Error, "whip", "unknown publisher error");
        }
        if (stopping_) break;
        media_queue_.discard_all();
        std::unique_lock<std::mutex> lock(wait_mutex_);
        wait_changed_.wait_for(lock, std::chrono::seconds(3), [this] { return stopping_.load(); });
    }
}

publish_once() 裡任何一步出錯都丟例外：ICE gathering 5 秒沒完成、POST 不是 201、媒體 track 15 秒沒打開（track->isOpen()，ICE 與 DTLS 都完成後才會是 true）、連線持續中斷。 一般的例外被 run() 接住、記 log、清空佇列、等 3 秒，然後從頭建一個新的 PeerConnection。 這讓本 repo 能在伺服器重啟、網路斷掉一陣子之後自己恢復，cpp 做不到。 唯一的例外是第 8 節的 UnrecoverableWhipError（Location 缺少或跨網域）：run() 直接 return，推流停止到程式重啟為止。

11. 收尾：DELETE 與關機（步驟 ⑨）

兩邊都在結束時對 Location 網址送 DELETE（帶同一份 token），告訴伺服器「這個 session 可以收掉了」。 沒送的話，伺服器要等自己的逾時機制才會清掉。

  • cpp：只在 node 關閉（解構子）時送一次，逾時是連線 3 秒、總共 5 秒。關閉順序寫得很小心：先停 GLib main loop、等 HTTP 執行緒結束，才 DELETE、才拆 pipeline，避免 callback 在拆到一半時觸發。
  • 本 repo：每一次 publish_once() 結束（包括每次重連前）都送 DELETE，逾時是總共 2 秒（POST 仍是 10 秒），而且不能被 stop() 中斷。request() 的第五個參數是「要不要中止」的旗標：POST 時傳的是 stopping_，stop() 一設它，請求就中止；收尾的 DELETE 傳的卻是 close_resource 裡新宣告、永遠是 false 的 std::atomic<bool> allow_cleanup{false}，所以 stop() 管不到它。遇到沒回應的伺服器，關機最久多卡約 2 秒。第一版（8754f65）的 DELETE 逾時是 10 秒，而且 ICE gathering 的 5 秒等待也叫不醒；現在的 wait_for_gathering 每 100 毫秒檢查一次停止訊號。

14. 常見錯誤

啟用 WHIP 後在 repo 根目錄啟動

症狀：只想試試錯誤訊息，結果畫面被送上雲端。

後果：啟用 WHIP 時，load_token() 會讀目前目錄的 .env。本 repo 根目錄如果放著含 WHIP_TOKEN 的 .env，env -u WHIP_TOKEN 擋不住。範例設定檔預設關閉 WHIP。

正解：做實驗時 cd 到沒有 .env 的目錄，並先確認 ls -a 裡沒有它；第 5 步的指令會自動做這個檢查。

範例設定檔的網卡名稱在 Jetson 上不存在

症狀：啟動就失敗，錯誤是 webrtc.host_interfaces has no interface present on this host。

Python 版 webrtcbin 印出 should not be reached

症狀：CRITICAL **: … gst_webrtc_bin_set_local_description: should not be reached，拿不到 offer。

後果：寫成 promise.get_reply().get_value('offer') 時，reply 是暫時物件，取出來的 offer 已經被釋放。

正解：先 reply = promise.get_reply() 存起來，再取 offer（第 3 步的腳本就是這樣寫的）。

啟用 WHIP 卻沒設 token

症狀：WHIP_TOKEN is required when whip.enabled is true，結束碼 2。

後果：WHIP 模組拒絕啟動；只測 RTSP 時不需啟用 WHIP。

正解：要推雲端時才把 whip.enabled 改成 true，並設定 token。

DELETE 忘了帶 token

症狀：程式關閉時 DELETE 回 401。

後果：伺服器上的 session 沒被收掉，只能等伺服器自己逾時清理。

正解：POST 與 DELETE 都要帶 Authorization: Bearer。兩邊的程式都有做；cpp 的註解特別寫了這件事。

出處：skai-edge-cpp delete_whip_resource() 的註解

webrtcbin 啟動後一直沒有送 POST

症狀：cpp 的推流 node 啟動了，但遲遲沒有 POST offer 到 WHIP 那行 log。

後果：webrtcbin 要從 rtph264pay 拿到含 SPS/PPS 的 caps 才會建 offer，而那要等第一張畫面進來。上游沒送畫面就永遠不會開始。

正解：先確認 h264_lo topic 有資料。這是預期行為，不是 bug。

出處：skai-edge-cpp CLAUDE.md 的 selfhost_publisher_node 說明

Location 被拒，session 沒收掉

症狀：本 repo 印一次 WHIP 201 omitted Location; automatic retry stopped 或 WHIP Location has a different origin; automatic retry stopped，之後推流就停了。

後果：伺服器已經回 201、建了 session，但 location 在賦值前就丟例外，收尾時跳過 DELETE，所以這一個 session 要等伺服器自己逾時清理。第一版（8754f65）還會每 3 秒重試、每次多留一個；29c3da1 改成停止重試，只會留這一個。

正解：部署前確認伺服器回的是同網域的 Location。出現這行 log 時，修好伺服器設定再重啟程式。

出處：Step 27 code review；src/webrtc/whip_policy.cpp 的 whip_resource_url

兩個專案同時推同一個 channel

症狀：觀眾畫面跳來跳去，或其中一邊一直被拒。

後果：兩邊預設都推到 /sfu/cam1/whip。minisfu 遇到同一個 channel 有第二個推流端會怎樣，本章沒有查證（推論）。

正解：同一時間只開一邊，或改用不同的 channel 網址。

15. 小結、目前限制與自我測驗

小結

  • WHIP 推流 = 一次 HTTP POST 交換 SDP（offer / answer），之後影像走 ICE 找到的 UDP 路、用 DTLS/SRTP 加密送出，結束時 HTTP DELETE。
  • 兩個專案都自己寫 WHIP 的 HTTP 那一層；最大的差別在 ICE 交給誰。重新編碼與斷線重試則是各自的設計選擇，跟函式庫無關。
  • cpp：webrtcbin ＋ libnice，有 STUN/TURN，送重新編碼的 480p，斷線不恢復。
  • 本 repo：libdatachannel ＋ 自寫的 skai-ice，只有 host 候選，送原始 H.264；持續斷線才重建 session。

目前限制與後續修正

  • 沒有 STUN / TURN：在擋 UDP 或 NAT 很嚴格的場地可能連不上。有三條路，代價不同：
    1. 先實測，不改程式：在實際部署的網路跑一次端到端推流，確認只有 host 候選夠不夠用（第 7 節的連線方式目前是推論）。成本最低；連得上的話，就不必現在付出下面兩條的代價。建議先做這一條。

      下面的做法本章作者沒有實際跑過（跑了就會把攝影機畫面推上雲端），是依程式碼整理的。

      需要：接得到攝影機的設定檔（video.rtsp_url 改成你的攝影機，webrtc.host_interfaces 改成你的網卡，whip.enabled: true）； 推流 token（跟管 minisfu 的人拿），放在環境變數 WHIP_TOKEN，或放進執行目錄下的 .env，一行寫 WHIP_TOKEN=<token>。 然後在 repo 根目錄執行 ./build/skai-edge --config <你的設定檔>。

      算連上：log 依序出現 module=whip message="publisher session created" 與 message="first H.264 access unit sent"， 之後不再出現 whip 的錯誤；再用瀏覽器開 https://skai-cam.duckdns.org/watch（skai-edge-cpp 設定檔註解寫的觀看入口）看得到畫面。

      算沒連上：出現 publisher session created 之後，約 15 秒內出現 WHIP media track did not open 或 WHIP ICE connection failed or remained disconnected，並每隔幾秒重複整個循環。 這代表 HTTP 那一段通了（伺服器收下 offer、回了 answer），但 ICE 找不到能通的 UDP 路，正是第 7 節那些條件有一個不成立。

      沒連上之後：這時才在下面兩條之間選。想守住 ROADMAP 的架構，選 2；急著在這個場地上線、願意改架構，選 3。無論選哪條，先把「哪個場地、什麼網路、失敗的 log」記下來，那是說服別人改架構的依據。

    2. 補強 skai-ice：加上 srflx（問 STUN）與 relay（TURN）候選。這是 ROADMAP 第 19 條指定的方向，架構規則不用改。代價是工作量大：TURN 用戶端要處理向伺服器申請中繼位址、權限、轉送封包，而且要在 skai-ice 那個獨立 repo 裡做；區網觀看與雲端推流用的是同一套 ICE，兩邊會一起受影響。
    3. 只讓 WHIP 改用 webrtcbin ＋ libnice：STUN/TURN 立刻可用，cpp 已經證明這樣做可行。代價是推翻 ROADMAP 第 15、17 條：執行檔裡會有兩套 ICE、兩套 WebRTC 函式庫要維護，也得先重新評估「只用 skai-ice」這個決定本身。 技術上它跟 libdatachannel 放得進同一個程式：libnice 的函式不叫 juice_*，也不受 USE_SYSTEM_JUICE 管，不會撞名。 但 cpp 證明的只是「webrtcbin 推得了 WHIP」，不是「它能跟 libdatachannel 住在同一個程式裡」；webrtcbin 還需要自己的 GLib main loop 執行緒（第 8 節），要另外整合進本 repo 的模組生命週期。 （改用原版 libjuice 在同一個執行檔裡做不到，見第 4 節。把 WHIP 拆成另一支獨立程式，技術上就能各用各的 ICE，但第 15 條講的是「this application」，拆開算不算違反，要由訂規則的人決定。）
  • 範例設定檔預設關閉 WHIP；正式推流需明確啟用並提供 token。
  • 短暫 Disconnected 可在同一個 session 恢復；超過寬限時間才重連。
  • 201 缺少或跨 origin 的 Location 仍可能留下一個無法安全刪除的伺服器 session；用戶端會停止自動重試，避免持續累積。
  • 停止等待：ICE gathering 約每 100 毫秒檢查停止訊號，DELETE 最長等待 2 秒。
  • 對雲端的端到端推流：本章作者沒有實測。另一個 session 在 Step 27 修正時回報，曾在這台 Jetson 目前的網路上實測取得 201、ICE 完成並送出 H.264 access unit；那次的輸出沒有收進本章，這裡也無法重現。換到其他部署場地時，仍要照選項 1 各測一次。

自我測驗

Q1. WHIP 的 HTTP POST 裡放的是影像資料嗎？

不是。POST 的 body 是 SDP offer（純文字的「自我介紹」），回應是 SDP answer。影像是之後走另一條 UDP 連線、用 SRTP 送的，完全不經過 HTTP（圖 27.2 的 ⑧）。

Q2. 本 repo 的 offer 只有 172.16.1.50 一個候選位址，為什麼還有機會連上雲端？什麼情況會連不上？

雲端伺服器有公開 IP，會寫在 answer 裡。Jetson 先往那個位址送 ICE 檢查封包，NAT 就會為這個埠開一條回程的路，伺服器可以沿著它回應（peer-reflexive）。 如果對外 UDP 被擋、NAT 太嚴格、或伺服器不接受 peer-reflexive，就連不上，而且沒有 TURN 可以退。（本章對這點是推論；另有一次在這台 Jetson 網路上成功的回報，見目前限制。）

Q3. 為什麼本 repo 在佇列掉畫面之後，要丟掉後面的畫面直到下一張 keyframe？

非 keyframe 的畫面只記錄「跟前一張差在哪」。中間少了一張，後面的差異就套不上去，觀眾會看到花屏。等到下一張可以單獨解碼的 keyframe，畫面才重新正確。

Q4. token 要帶在哪些請求上？RTP 影像封包要帶嗎？

POST（建立 session）與 DELETE（結束 session）都要帶 Authorization: Bearer。RTP 封包不帶；它的安全性靠 DTLS 握手時核對 SDP 裡的 fingerprint。

Q5. 在同一台 Jetson 上，cpp 的 webrtcbin 列出 12 個 host 候選，本 repo 只列 1 個。差在哪兩件事？

一、webrtcbin 會列出所有網卡上的所有位址（含 Tailscale 與 IPv6），本 repo 只用設定檔白名單裡的網卡。二、webrtcbin 每個位址都列 UDP 與兩種 TCP，skai-ice 只做 UDP。

Q6. 如果伺服器重開機，兩個專案各自會發生什麼事？

cpp：連線變成 FAILED，印一行 log，之後不再嘗試，要人工重啟 node。本 repo：連線變成 Failed，或斷線超過 10 秒，publish_once() 就丟例外，run() 等 3 秒後重建 PeerConnection 重新 POST；伺服器回來之後會自己接上。

Q7. 既然 libdatachannel 原本的 libjuice 支援 STUN/TURN，為什麼不讓 WHIP 這一路改用它就好？

USE_SYSTEM_JUICE 是整個 libdatachannel 的建置開關，不能每條連線各自選；skai-ice 又實作了同一組 juice_* 函式，兩者不能同時連進一個執行檔（CMakeLists.txt 偵測到多一份 libjuice 就會 FATAL_ERROR）。而且 ROADMAP 第 15 條規定整個程式只能有 skai-ice 一套 ICE。
