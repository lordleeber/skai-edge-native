STEP 28

1. 為什麼需要這一步

區網裡的瀏覽器早就看得到框。它走兩條路：影像走 WHEP（WebRTC），偵測結果另外走 WebSocket，每一筆結果帶著它那一幀的 PTS（攝影機給的呈現時間，單位奈秒）。 瀏覽器把 PTS 換算成 RTP 時間戳，等到畫面播到同一個 RTP 時間戳時才把框畫上去（web/app.js 的 presentDetectionFrame）。 這行得通，是因為區網 WHEP 的 RTP 時間戳就是直接從 PTS 算的（Step 27 第 9 節的 h264_rtp_timestamp），兩邊用同一把尺。

雲端 /watch 沒有這條 WebSocket。要補上它，最直覺的做法是「另開一條管道送偵測結果」，但雲端那台 minisfu 有三個特性，讓這條路走不通或很麻煩：

  • 它只轉發 RTP 的 payload：影像封包的內容一個 byte 都不改，原樣轉給每個觀眾（infra repo 的 sfu/src/rtp.hpp）。
  • 它會拿掉 RTP header extension：RTP 封包標頭後面可以掛額外資料，但 minisfu 轉發時會把它丟掉，所以不能藏在那裡。
  • 它沒有 data channel：WebRTC 除了影音還能開一條傳任意資料的通道，但 minisfu 完全沒有實作。

反過來說，只要資料在 H.264 本身裡面，minisfu 就一定會原封不動地送到觀眾手上。 H.264 標準剛好預留了一種叫 SEI 的「附加資訊」單位，解碼器看不懂就直接略過，不影響畫面。這就是 Step 28 的載體。

這個做法由 edge 端（本 repo）與 infra 端（skai-edge-streaming-infra）在 2026-09-24 談定，寫進 ROADMAP.md 的 Step 28，叫做 SEI 契約 v1。 兩邊分工很清楚：本 repo 負責把 SEI 插進要送出的畫面，infra 負責 /watch 讀出 SEI、畫框；minisfu 一行都不用改。 契約是雙方的約定，之後要改任何欄位都要兩邊同意，所以本章多次提到「規格沒動」。

2. 這一章新出現的詞

Step 27 已經講過 access unit、keyframe、SPS/PPS、RTP 時間戳。下面是這一章新增的詞，讀到卡住時回來查。

詞一句話解釋
NAL unit（NAL）H.264 資料的最小包裝單位。一個 access unit（一幀畫面）由好幾個 NAL 組成，每個 NAL 的第一個 byte 是 header，低 5 bit 是它的類型（type）。
Annex-B 與 start code把 NAL 一個接一個串在一起的格式。每個 NAL 前面放 00 00 01（3 byte）或 00 00 00 01（4 byte），叫 start code，解碼器靠它找出 NAL 的邊界。本 repo 從 RTSP 拿到的 access unit 就是這種格式。
VCL NAL / slice真正裝著畫面像素資料的 NAL（type 1～5），也叫 slice。type 5 是 keyframe 的 slice（IDR），type 1 是一般畫面。
非 VCL NAL不裝像素、只裝附加資訊的 NAL。這章會遇到：AUD（type 9，access unit 分隔符號）、SPS（type 7）、PPS（type 8）、SEI（type 6）。
SEISupplemental Enhancement Information，H.264 的「附加資訊」NAL。裡面可以放好幾則訊息，每則有一個 payloadType。解碼器不需要它也能解出畫面。
user_data_unregisteredpayloadType 5 的 SEI 訊息：開頭 16 byte 是一個 UUID，後面隨便放自己的資料。UUID 用來認出「這是誰放的資料」，別人的 SEI 就不會被誤讀。
UUID128 bit（16 byte）的識別碼，通常隨機產生，幾乎不可能撞號。Step 28 的是 197c65ee-a132-4f53-85a0-8af9ad153c4b。
RBSP / 防撞碼（emulation prevention）NAL 內容的「原始版」叫 RBSP。因為 00 00 01 代表下一個 NAL 開始，內容裡不可以出現這串 byte，所以寫進 NAL 前要在連續兩個 00 後面、下一個 byte ≤ 03 時插一個 03。插進去的那個 03 叫 emulation prevention byte，本章叫它防撞碼。
Frame 與 access unit本 repo 裡同一幀畫面的兩種形態。EncodedAccessUnit 是攝影機送來、還沒解碼的 H.264，給 WHEP、WHIP、錄影轉送；Frame 是 GStreamer 解碼後的像素（BGR），給 YOLO 推論。兩者出自同一條 RTSP pipeline。
PTSPresentation Time Stamp，這一幀「應該在什麼時間播」，GStreamer 給的單位是奈秒。
tick（90 kHz）H.264 RTP 時間戳的單位，1 tick = 1/90000 秒。25 fps 時一幀是 3600 tick。
dtStep 28 自己定義的欄位：「帶著這則 SEI 的那一幀」和「被推論的那一幀」之間差幾個 tick。第 6 節詳細講。
generation（世代編號）Step 28 加的計數器：RTSP 模組每重建一次 GStreamer pipeline 就加 1，並蓋在那條 pipeline 產生的每一幀上。第 9 節詳細講。
TensorRT 引擎檔（.engine）把 YOLO 模型針對某一種 NVIDIA GPU 編譯好的檔案，推論模組啟動時載入它。它跟 GPU 型號綁定，不放在 git 裡；本 repo 的測試與範例假設它在 /var/lib/skai-edge/models/yolo11s_fp16.engine（fp16 指用 16 位元浮點數計算）。本章不講怎麼產生它，一般是用 TensorRT 附的 trtexec 從 .onnx 模型轉出來。
Encoded Transform瀏覽器的 WebRTC API，讓網頁在解碼之前拿到每一幀的原始位元組。/watch 靠它讀出 SEI。這是 infra 端的事，本章只提到它的存在。

3. 一筆偵測結果的完整旅程

從攝影機送來一幀畫面，到雲端觀眾看到這一幀上的框，中間經過八站。圖上每一站都可以點，會跳到對應的小節；後面小節標題的「（步驟 ④）」這類標記，用的就是這張圖的編號。

先記住一件事：推論需要時間（這台 Jetson 上約 30 ms），結果出來時，它那一幀通常已經送出去了。 所以 SEI 永遠附在比較晚的某一幀上，裡面的 dt 告訴觀眾「往回數多少 tick 才是這個框真正屬於的那一幀」。整個設計都圍繞這件事。

兩個地方值得停一下：

  • 長度超過 255 怎麼寫：一個 byte 最多表示 255。H.264 的規則是先寫若干個 0xFF（每個代表「再加 255」），最後一個不是 0xFF 的 byte 是餘數。 例如長度 316 寫成 FF 3D（255 ＋ 61）。上面 while 迴圈就是在做這件事。
  • 防撞碼：內容裡只要出現連續兩個 00，而下一個 byte 又 ≤ 03，就先插一個 03。 這樣內容裡永遠不會出現 00 00 01，解碼器找 NAL 邊界時就不會被騙。觀眾端讀的時候做相反的事：看到 00 00 03 就把 03 拿掉。
  • 結尾為什麼是 0x80：H.264 規定 NAL 內容最後要放「一個 1 bit，後面補 0 到滿一個 byte」（rbsp_trailing_bits），標示內容在這裡結束。我們的內容剛好都是整數個 byte，所以就是 1000 0000，也就是 0x80。

我們自己的 SEI 其實永遠不會觸發防撞碼：UUID 裡沒有 00，JSON 是可見字元，長度 byte 最多一個 00。 這是 infra 端寫測試時發現的：用真的 UUID 測防撞碼，等於沒測。所以本 repo 的測試（和第 11 節的實驗二）改用全是 0 的假 UUID，才逼得出 00 00 03。

JSON 的欄位

欄位意思
v契約版本，固定是 1。
r結果的陣列，由舊到新排。一則 SEI 可能帶好幾筆結果（推論慢了、好幾筆擠在一起時）。
dt這筆結果的那一幀，比「帶著這則 SEI 的那一幀」早多少 tick。第 6 節。
b框的陣列。每個框是 [x, y, w, h, "類別名", 分數]：左上角座標和寬高，都除以畫面寬高，所以是 0～1 的比例，四捨五入到小數 4 位；分數也是 0～1。
"b": []這筆推論沒有偵測到任何東西。觀眾端看到它就清掉舊框。反過來，一幀畫面完全沒有 SEI 代表「沒有新結果」，觀眾端保留舊框；超過 1 秒都沒有新結果才自動清掉。

座標用比例而不是像素，是因為觀眾端的 <video> 會被縮放，比例乘上它實際顯示的寬高就能畫。 數字的寫法也刻意固定：0.1 而不是 0.1000，1 而不是 1.0，而且不受系統語系影響（有些語系的小數點是逗號，會寫出不合法的 JSON）。 normalize_sei_box 另外會把超出畫面的座標夾回 0～1，並把模型偶爾吐出的 NaN（「不是數字」的浮點值）變成 0；這是 28-a code review 抓到、再補上的。

5. 插在畫面的哪裡（步驟 ⑥）

契約規定 SEI 要放在這一幀第一個 slice 之前。H.264 本身就要求 SEI 出現在同一個 access unit 的 slice 前面； 觀眾端的解析器也利用這一點，一看到 slice 就停止掃描，不必讀完整張畫面（keyframe 可能有幾十 KB）。

src/webrtc/detection_sei.cpp
bool insert_before_first_vcl(std::vector<std::uint8_t>& access_unit,
                             const std::vector<std::uint8_t>& nal) {
    for (std::size_t i = 0; i + 3 < access_unit.size(); ++i) {
        if (access_unit[i] != 0 || access_unit[i + 1] != 0 || access_unit[i + 2] != 1) {
            continue;
        }
        if (is_vcl(access_unit[i + 3])) {
            // Keep a 4-byte start code's zero_byte with the slice it introduces.
            const auto at = i > 0 && access_unit[i - 1] == 0 ? i - 1 : i;
            access_unit.insert(access_unit.begin() + static_cast<std::ptrdiff_t>(at),
                               nal.begin(), nal.end());
            return true;
        }
        i += 2;
    }
    return false;
}

它一路找 00 00 01，看後面那個 NAL header 是不是 slice（is_vcl 檢查 type 是否在 1～5）。找到第一個 slice 就把 SEI 插在它的 start code 前面。 at 那一行處理 4 byte 的 start code：00 00 00 01 最前面那個 00 要跟著 slice 一起往後移，否則會變成「前一個 NAL 尾巴多一個 00」。 兩種結果解碼器都接受，但保持完整比較乾淨，測試也把這個位置固定住了。 一幀裡如果找不到 slice，函式回傳 false，畫面不動；正常的攝影機串流不會出現這種畫面。

6. dt：告訴觀眾「這個框屬於哪一幀」（步驟 ⑤⑧）

回到第 3 節的那個事實：結果附在比較晚的那一幀上。觀眾端要把框畫在正確的那一幀，得知道「原本那一幀的 RTP 時間戳」。 最直接的想法是把原本那一幀的時間戳直接寫進 SEI，但這在雲端行不通：

  • minisfu 會改時間戳：它替每個觀眾維護一個時間戳偏移（tsOffset）。觀眾第一次加入時偏移是 0，但推流端重新推流之後，偏移會變（infra repo 的 sfu/src/sfu.cpp）。edge 這邊寫進去的絕對時間戳，到了觀眾手上可能已經不是同一個數字。
  • RTSP 重連之後，edge 自己也會改時間戳：第 9 節會講，WHIP 的 RTP 時間戳在重連後不再等於 PTS 換算值。

不管誰加了多少偏移，同一條串流裡兩幀之間的「差」不會變。所以契約寫的是相對值 dt：

ROADMAP.md（Step 28，Field rules，節錄）
- `dt = round((pts_attach - pts_source) * 90000 / 1e9)`, an integer >= 0, where
  `pts_attach` is the PTS of the access unit carrying the SEI
src/webrtc/detection_sei.cpp
std::optional<std::uint32_t> sei_dt_ticks(std::uint64_t attach_pts_ns,
                                          std::uint64_t source_pts_ns) {
    if (source_pts_ns > attach_pts_ns) return std::nullopt;
    const auto elapsed = attach_pts_ns - source_pts_ns;
    // round(elapsed * 90000 / 1e9) == round(elapsed * 9 / 100000)
    return static_cast<std::uint32_t>((elapsed * 9 + 50'000) / 100'000);
}

90000 / 1e9 約分之後是 9 / 100000；加上 50000 再整數相除，就是四捨五入。全程用整數運算，不會有浮點誤差。 如果來源那一幀比附著的那一幀還晚（不應該發生），函式回傳「沒有值」，由第 7 節的挑選規則把它丟掉。

觀眾端的規則（infra 的 sei.js）是：播放第 X 幀時，畫「來源時間戳 ≤ X」的最新一筆結果，來源時間戳 = 帶 SEI 那幀的時間戳 − dt。 所以觀眾端也要求 r 由舊到新：它收到一筆比佇列尾端還舊的結果，會把尾端清掉。這是第 7 節排序規則的由來。

實測時 dt 的中位數是一幀（第 11 節）：推論大約 30 ms，比一幀的間隔短，所以結果幾乎都趕得上下一幀。

7. 每一幀要附哪些結果（步驟 ④）

WHIP 每要送出一幀，就問 SeiResultSelector：「等在這裡的結果，有哪些要附在這一幀上？」規則來自契約的 Emission rules：

規則為什麼
只附在 WHIP 真的要送出的畫面上WHIP 在等 keyframe、或連線暫停時會丟掉畫面。附在被丟掉的畫面上，結果就跟著消失了。
只留1 秒內的結果觀眾端 1 秒沒有新結果就清框；更舊的結果畫出來也只是閃一下的錯誤框。
丟掉RTSP 重連前的結果重連後 PTS 從 0 重新算，舊 pipeline 的 PTS 跟新的不能相減。

9. RTSP 重連：時間戳不能倒退（步驟 ①）

RTSP 連線斷掉時，本 repo 會把整條 GStreamer pipeline 拆掉重建。新 pipeline 的 PTS 從頭算起：實測每次重建後，第一幀的 PTS 約 0.52 秒。 Step 27 的 WHIP 直接用 PTS 換算 RTP 時間戳，所以重連之後，同一條 WHIP 串流（同一個 SSRC）的時間戳會突然倒退，例如從 10 秒倒退回 0.5 秒。

minisfu 只在推流端重新建立 session 時重算偏移，同一個 session 裡的倒退會原封不動地送到觀眾那裡。 觀眾端的播放器會以為時間倒流；Step 28 的觀眾端佇列也要求來源時間戳遞增，倒退會讓它清掉還沒畫的結果。 所以契約另外規定：重連時，WHIP 的 RTP 時間戳要從上一次送出的值加一幀繼續往前。區網 WHEP 不改，因為區網的疊框靠的正是「時間戳 = PTS 換算」。

怎麼知道「重連了」：三次設計

這一段是 Step 28 裡最值得看的演進。同一個問題改了三次，每一次都是被某個具體情況推翻：

  1. 第一版（28-a）：看 discontinuity 旗標。RTSP 模組會在新 pipeline 的第一幀標上 discontinuity = true，WHIP 看到就重新接續。 但 WHIP 在等 keyframe 時會跳過畫面，旗標所在的那一幀可能根本沒送出；所以旗標要「記住」，直到下一個真的送出的畫面。 這還不夠：WHIP 暫停或佇列滿了會直接丟掉畫面，帶旗標的那一幀如果被丟了，WHIP 就永遠不知道重連過。
  2. 第二版（28-a 自己發現的洞）：PTS 沒往前就當成重連。只要算出來的時間戳沒有比上一個大，就重新接續。 code review 指出這會漂移：遇到重複或稍微亂序的 PTS，每次都「接續一幀」，偏移一路往前累積，再也回不來。
  3. 第三版：世代編號。與其猜「是不是重連了」，不如讓每一幀自己帶著答案。 28-a 的 review 修正先在 WhipPublisher 收到畫面時自己數旗標；28-b 再把它移到知道答案的源頭： RtspSource 每重建一次 pipeline 就把 pipeline_generation_ 加 1，蓋在那條 pipeline 產生的每一個 Frame 與 access unit 上。 每一幀都帶著編號，丟掉哪一幀都不影響判斷；同一個世代裡 PTS 怎麼跳，也不會觸發重新接續。

WhipRtpClock

src/webrtc/whip_policy.cpp
std::uint32_t WhipRtpClock::timestamp(std::uint64_t generation, bool has_pts,
                                      std::uint64_t pts_ns) {
    if (has_last_ && generation != generation_) last_pts_ticks_.reset();
    generation_ = generation;
    std::uint32_t next = has_last_ ? last_ + frame_ticks_ : start_;
    if (has_pts) {
        const auto ticks = h264_rtp_timestamp(pts_ns);
        if (has_last_ && !last_pts_ticks_) {
            // First PTS after a restart or after units without PTS.
            offset_ = next - ticks;
        } else if (last_pts_ticks_) {
            const auto step = static_cast<std::int32_t>(ticks - *last_pts_ticks_);
            // Learn the frame interval from consecutive units at 10 fps or faster.
            if (step > 0 && step <= 9000) frame_ticks_ = static_cast<std::uint32_t>(step);
        }
        next = ticks + offset_;
        last_pts_ticks_ = ticks;
    }
    last_ = next;
    has_last_ = true;
    return next;
}

讀法：

  • 平常：時間戳 = PTS 換算 ＋ offset_。一開始 offset_ 是 0，所以跟 Step 27 完全一樣。
  • 世代變了：忘掉上一個 PTS（reset()）。下一個有 PTS 的畫面就會進入「重新接續」那一支：把 offset_ 設成「上一個送出的值 ＋ 一幀 − 新的 PTS 換算值」，從此新 pipeline 的時間戳都接在舊值後面。
  • 「一幀」是多少：用最近兩個連續畫面的 PTS 差（只接受 10 fps 以上，也就是 ≤ 9000 tick 的差），還沒學到就用 3000（假設 30 fps）。 28-a code review 抓到一個 bug：第一版會把「還沒有上一個 PTS」時的佔位值 1 當成幀間隔學進去，重連後只往前 1 tick。
  • 時間戳是 32 bit，約 13 小時會繞回 0。static_cast<std::int32_t>(ticks - …) 用有號數看差值，繞圈時的差仍然是正的一幀。

12. 常見錯誤

八格都是這一步真的發生過的：有的是程式的 bug（含 code review 抓到的），有的是測試寫錯或測試本身卡住，最後一格是解讀量測數字時的誤判。

sink 收到空的偵測結果

症狀：雲端每一則 SEI 都是 "b": []，區網卻看得到框。

後果：commit_detections 的參數是傳值，std::move(published) 在呼叫當下就把向量搬走，commit lambda 裡再讀 published 只剩空的。

正解：在 move 之前先複製一份給 sink（第 8 節）。用 Jetson 整合測試比對 sink 與 API 的框數才抓得到。

「PTS 沒往前就當重連」會漂移

症狀：推流越久，WHIP 的 RTP 時間戳跑得越前面。

後果：重複或稍微亂序的 PTS 每次都觸發「接續一幀」，偏移只增不減。

正解：由 RTSP 模組在每一幀蓋世代編號，只有世代變了才重新接續（第 9 節）。

出處：Step 28-a code review

帶旗標的那一幀被丟掉

症狀：RTSP 重連後 WHIP 時間戳還是倒退了。

後果：discontinuity 只標在新 pipeline 的第一幀；WHIP 暫停或佇列滿時，那一幀可能被丟掉，WHIP 就不知道重連過。

正解：同上，改用每一幀都帶的世代編號。

用真的 UUID 測防撞碼

症狀：防撞碼的測試一直通過，把防撞碼整段拿掉也照樣通過。

後果：我們的 UUID 與 JSON 裡永遠不會出現兩個連續的 00，測試根本沒走到那段程式。

正解：測試改用含很多 00 的假 UUID，並用「故意改壞程式、看測試會不會失敗」確認它守得住。

出處：infra 端做 /watch 疊框時的踩坑紀錄；本 repo DetectionSei.EmulationPreventionRoundTripsZeroRuns

把合法的 00 00 80 當成錯誤

症狀：防撞碼的測試失敗，說 00 00 後面不是 03。

後果：那條測試的內容故意以兩個 00 結尾，後面接結尾位元 80，所以編出來的 NAL 最後是 00 00 80。只有 00 00 後面接 00～03 才需要插防撞碼，00 00 80 本來就合法。第一版測試寫得太嚴，錯的是測試。

正解：斷言改成「00 00 後面的 byte 必須 ≥ 03」。

第一幀把佔位值 1 學成幀間隔

症狀：推流只送過一幀就遇到重連，重連後時間戳只往前 1 tick。

後果：還沒有上一個 PTS 時，程式用 1 當佔位的差值，剛好落在「10 fps 以上」的範圍裡，被當成真的幀間隔。

正解：只有兩個連續畫面都有 PTS 時才學幀間隔；還沒學到就用 3000。

出處：Step 28-a code review

假伺服器在測試結束時卡住

症狀：端到端測試的斷言全部通過，程式卻停在結尾不動，最後被 ctest 的逾時砍掉。

後果：假伺服器用 Boost.Asio 的 acceptor（在一個埠上等新連線的物件）；它的 accept() 會一直等到有人連進來才回傳。原本以為在另一條執行緒呼叫 acceptor 的 close() 會叫醒它；在 Linux 上不會。

正解：解構時先自己連一次那個埠，讓 accept() 回來，再 join 執行緒。

用 tick 數比較 dt

症狀：dt 中位數從 3610 變成 4698，以為延遲變差了 30%。

後果：一幀的 tick 數取決於攝影機幀率（25 fps 是 3600、19 fps 約 4700）。攝影機換了幀率，tick 數就跟著變。

正解：用「送出的幀數 ÷ 秒數」算出實際幀率，把 dt 換成幾幀再比（第 11 節）。

13. 小結、目前限制與自我測驗

小結

  • 雲端 minisfu 只原樣轉發影像 payload，所以偵測結果寫成 H.264 SEI（payloadType 5 ＋ 固定 UUID ＋ JSON），插在畫面第一個 slice 前面，跟著影像走。
  • 結果附在推論完成後、WHIP 下一個真的送出的畫面上；dt 記錄兩幀的相對距離，不受 minisfu 或 edge 加的時間戳偏移影響。
  • 挑選規則：1 秒內、同一個世代、不比這一幀新、由舊到新、整則 ≤ 1024 byte；太大先丟最舊的結果，再截掉低分的框。
  • RTSP 重連靠世代編號判斷，WHIP 的 RTP 時間戳接續舊值、不倒退；區網 WHEP 與錄影完全不受影響。

目前限制

  • 雲端畫面沒有用眼睛驗過：需要有人推流時同時開 /watch?debug=1（infra 端提供的除錯模式，左下角顯示 SEI 的狀態）確認框畫對。這也是 infra 端還沒完成的「真的 edge 串流驗收」。
  • 每則 SEI 約 20 個框：同一幀物件更多時，雲端觀眾看不到分數較低的那些。要放寬，得改規格（例如座標改 3 位小數）或提高上限（多吃頻寬），都要跟 infra 端重新談。
  • 沒有 track_id：契約允許第 7 個欄位放追蹤編號，但本 repo 還沒有物件追蹤，所以省略。
  • 計數器只在 session 結束時印出：推流進行中看不到 SEI 的統計，要等關閉或重連時的那一行 log。之後 Step 29（Metrics）可以把它接進 metrics。

自我測驗

Q1. 為什麼不另外開一條 WebSocket 或 data channel 把偵測結果送到雲端？

minisfu 沒有 data channel，也會拿掉 RTP header extension；另開 WebSocket 則要自己處理時間對齊與認證。只有 H.264 payload 保證原封不動送到觀眾手上，所以把結果寫進 SEI，放進影像本身。

Q2. 一則 SEI 的 JSON 有 64 byte，payloadSize 那個 byte 為什麼是 0x50（80）而不是 64？

payloadSize 算的是整個訊息的內容：16 byte 的 UUID 加上 64 byte 的 JSON，共 80。

Q3. SEI 裡為什麼放相對的 dt，而不是被推論那一幀的 RTP 時間戳？

RTP 時間戳到了觀眾手上可能已經被改過：minisfu 在推流端重新推流後會改變每個觀眾的偏移，edge 在 RTSP 重連後也會加偏移。兩幀之間的差不受整體偏移影響，觀眾端用「帶 SEI 那一幀的時間戳 − dt」就能找回原本那一幀。

Q4. 最新一筆結果單獨就超過 1 KB 時，為什麼選擇截掉低分的框，而不是整筆不送？

觀眾端看到「這一幀沒有 SEI」會保留舊框，看到 "b": [] 會清框。整筆不送會讓畫面一直停在上一次的框，比少畫幾個低分框更糟。

Q5. 為什麼 Frame 也要蓋世代編號，只蓋 access unit 不夠嗎？

偵測結果來自解碼後的 Frame，WHIP 送的是 access unit。挑選結果時要判斷「這筆結果是不是重連前的」，必須拿結果的世代跟要送的那一幀的世代比；兩者都蓋同一個編號才對得上。

Q6. 如果 RTSP 重連時，帶 discontinuity 旗標的那一幀被 WHIP 的佇列丟掉了，現在的程式還會讓時間戳倒退嗎？

不會。WhipRtpClock 看的是每一幀都帶的世代編號，不是旗標；重連後第一個真的送出的畫面世代不同，就會從上一個送出的值加一幀接續。

Q7. 這一次實測 dt 中位數是 4698 tick，基線是 3610 tick。延遲變差了嗎？

沒有。基線當時攝影機約 25 fps（一幀 3600 tick），這次約 19.2 fps（一幀約 4700 tick）。兩次都是一幀。
